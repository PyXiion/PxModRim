Startup impact — redesign options

Problems with today's dialog: it only shows one mod at a time (the selected one); metric colours are a random 20-colour preset with no meaning; the donut/bar toggle shows the same three numbers; there is no way to see all mods ranked, which phases cost the most, or which mods were on/off the main thread. Data available: base-game phase metrics, per-mod metrics (main-thread + off-thread), report timestamp and total loading time. All mockups use the same fake data.

A — Ranked mods

Leaderboard. The answer to "what is slowing my startup?" in one glance: every mod ranked, each bar coloured by its dominant phase (same phase palette everywhere). Click a row for its own phase breakdown. Opened from a mod → that row is pre-selected and expanded.
  • Best for: finding culprits fast; closest to how users think ("which mod is slow").
  • Cost: smallest change — reuses the data model; one QML list + expandable delegate.

B — By phase

Diagnostic view. Rows are RimWorld loading phases (Loading defs, Textures, Patches, XML, static constructors…). Expanding a phase shows which mods spent time in it. Answers "why is Applying patches 40 s?". Side cards give the takeaways (top phase, top mod, off-thread share).
  • Best for: modpack builders tuning the load; makes the cryptic metric names meaningful (grouped into ~7 categories, raw name on hover).
  • Cost: needs a metric→category map in labels.py and per-phase mod aggregation in the service.

C — Timeline + treemap

Visual overview. Top: the load as a left-to-right timeline of phases (base game and mods together, true proportions with a time axis). Bottom: treemap where area = mod time, coloured by dominant phase; the mod selected in the main window is outlined. Insight cards call out concentration ("5 mods = 61 % of mod time").
  • Best for: an impressive at-a-glance picture, spotting one huge outlier.
  • Cost: highest — custom treemap layout (squarify) in QML/JS; small mods become unreadable slivers, so needs an "Others" cell and click-to-zoom.

Recommendation

A as the default view, with B as a second tab ("Mods | Phases") in the same dialog, sharing the phase palette and the summary stack on top. C is the flashiest but weakest for actually acting on the data. Whichever is chosen: replace the random colour preset with a fixed phase palette, and put the total + base/mods/off-thread split at the top.
